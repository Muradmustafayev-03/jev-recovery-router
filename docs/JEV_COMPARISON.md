# Optional paid Jev comparison

For the current A100 run, pass `--run runs/a100-001 --config configs/a100.json` to `scripts/run_jev_comparison.py` so its VM-budget calculation uses the A100 hourly rate. The H100 defaults remain available for historical runs.

**Completed retrospective comparison.** Jev 1.13.0 forecasts were collected through the API and evaluated on all three natural-test populations: CLINC with 120 intents (4,600 queries), CLINC with 150 intents (5,500 queries), and BANKING77 (3,080 queries). Results, costs, limitations and retry disclosures accompany the [published model card](https://huggingface.co/Quicksort-fr/jev-recovery-router). This is an independent complete-system comparison using our calibration and routing policies, not a native vendor benchmark. Collected HTTP timings do not provide a matched end-to-end latency comparison.

Run this comparator explicitly only when a paid comparison is wanted. It is not part of automatic training or tests. Supply `TYPESAFE_API_KEY` through the environment; the client neither prints nor persists it. Do not put the key in a command-line argument or commit it.

```bash
python -m recovery_router.jev --data data/processed/test.jsonl \
  --output runs/jev/test.jsonl --model jev-1.13.0 \
  --max-usd 1.00 --max-requests 20000 --input-price-per-million 0.042
```

The default unit price is a documented assumption, **not an invoice guarantee**. Verify current account pricing and the request token ceiling before paid use. The budget excludes taxes and extra provider fees. Sources: [API documentation](https://docs.typesafe.ai/api), [models/pricing](https://docs.typesafe.ai/models).

Each attempted request reserves `64,000 × assumed price / 1,000,000` dollars **before sending**, including errors/timeouts. At $0.042/M this is $0.002688 per request. After a validated success is durably written, the unused reservation is released and the budget retains **returned input tokens × configured price**. Failed, uncertain or interrupted requests retain their full reservation, including after restart. `--max-requests` is an additional cap counting every attempt, including errors. Returned usage is an estimate of the token charge, not a checked invoice. The finite reservation bound assumes no request bills more than 64,000 input tokens, the declared unit price, and free output; unexpected usage/model/response shapes stop the run.

Defaults are $1 and 20,000 attempts. A full 5,500-record test needs up to 11,000 requests, so it can fit these caps **if actual returned usage fits the dollar allowance**. As an arithmetic illustration, 1,000 input tokens per request would cost $0.462 for 11,000 requests at $0.042/M, excluding tax; this is not measured Jev usage. Calibration and policy-training predictions consume additional budget. Before each new request the ledger must still have room for a whole worst-case reservation, so it may stop slightly below the dollar cap.

The append-only cache journal defaults to `<output>.cache.jsonl`. A reservation is flushed to disk before network activity. Resume reconstructs charges from validated successes and full reservations for unresolved attempts. A process lock is held for the client's lifetime, so a second process cannot concurrently use the same ledger and race its budget. By default, timeouts, interrupted sends, invalid responses and HTTP failures, including 429, are not retried, even after restart. Explicit bounded retry options are described below. Inspect account usage before deliberately starting any replacement run. Do not delete/replace a ledger to claim that prior charges disappeared. Use the same explicit `--cache` path across dataset commands when one total dollar/request cap should cover them all.

The default remains one worker without retries. Both CLIs accept, for example, `--workers 4 --requests-per-second 8 --max-retries 3`. Workers keep the same separate first/expanded payloads, serialize budget reservations and journal writes, share duplicate responses, and preserve input row order. The request-rate cap covers every worker and retry. A positive `--max-retries` permits bounded HTTP 429/529 retries. `--retry-transient-http` additionally permits 500/502/503/504/520–524, and `--retry-uncertain-transport` permits allowlisted network failures within the combined HTTP/transport cap. Authentication failures remain terminal. `--max-validation-retries` separately permits a bounded fresh attempt after an HTTP-200 response fails strict validation; it does not normalize or accept invalid probabilities. These opt-ins can resample provider outputs and must accompany any resulting comparison's disclosure.

Recovery from older journals has separate explicit options: `--retry-legacy-unknown-transport` permits one charged diagnostic retry of a legacy transport failure without a recorded reason, within the combined retry cap; `--retry-legacy-cancelled` permits one fresh reserved attempt after a predispatch cancellation or a legacy no-status `RuntimeError` whose dispatch state is unknown. Every retry creates a new reservation; prior failed or uncertain reservations remain charged against the shared cap. Backoff honors a valid `Retry-After` value, and a delay above 60 seconds stops this bounded retry loop. Per-request retry limits persist across reopening the ledger. Timings in parallel mode describe successful HTTP attempts under concurrency, excluding retry waits, pacing and retrieval; they are not serial online-serving latency. The completed comparison used disclosed retry/recovery opt-ins, including a post-seal exception; consult the published model documentation when interpreting its results.

The first and expanded decisions use **separate requests**; the first request contains only first-stage candidates. Gold labels and diagnostic annotations never enter the request. Choices are keyed by ordered letters; `NONE` is always returned last in the output probability vector, retaining its full probability mass. Request hashes include model, observed query and the full question. Equal observations can reuse a response while preserving different dataset record IDs. Sanitized probability answers, usage, pinned returned model, dates, hashes and original HTTP timings are retained. Cache-hit timings denote the original remote observation, not local cache lookup performance. Retrieval and online networking location still affect an end-to-end comparison.

**Post-experiment client correction (2026-10-06):** A positive `--requests-per-second` now serializes synchronous transport calls and waits at least one configured request interval after each call completes. This conservative ceiling prevents a worker paused after admission from entering transport beside the next worker; actual throughput can be lower than the configured rate. `--requests-per-second 0` retains parallel transport calls up to the worker limit. Budget reservations, deduplication and retry accounting remain shared across workers. This change belongs to the public client and does not alter the source or timing records of the archived experiments.

If the budget or an error stops the run, output is **partial** and the CLI exits nonzero. The metadata marks it incomplete. Do not present this as a matched full-dataset benchmark or silently compare it with a different Qwen sample. Either complete the exact predeclared IDs for every compared method under an explicitly enlarged total budget, or predeclare a shared smaller subset before examining outcomes. Preserve natural and intervention partitions and identical candidate order. Calibration/policy training on Jev outputs needs separately budgeted, matched calibration/policy partitions; test-only predictions do not provide those.

The ledger and output contain benchmark predictions and identifiers and should be handled like the underlying data. Tests use injected fake HTTP transports and make no external requests.

Every prediction includes `model_fingerprint=api-version:<version>:choice-protocol-v1`, and its sidecar fingerprints the input data file. This identifies the pinned API version and this client's question protocol; **it is not a hash of TypeSafe's unavailable weights** and cannot independently rule out changes behind the same provider version. Request/response hashes identify the exact observed queries and returned probability snapshots.
